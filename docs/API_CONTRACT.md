# Контракт Exile Forge 2.5

Сервер: ветка `claude/tender-pasteur-a36kj2`, коммит `a1f4fbabe6dd3512cfb421031fc88b81324617cb` (ktor-bestgame 0.25.0).
Успех: `{"success":true,"data":...}`. Ошибка: `{"success":false,"error":{"message","errorClass","errorMethod","errorCode","messageArgs"}}`; HTTP-статус сохраняется клиентом.

`messageArgs` добавлено в 0.17.0 и чинит давнюю дыру: `message` — готовое английское предложение, а `error.<код>` в словаре почти всегда шаблон с дыркой («Уровень {0} слишком мал»). Заполнить её клиенту было нечем, и переводились только 17 кодов из 114 — те, у кого шаблон без дырок. Теперь конверт несёт то, что сервер подставил в своё предложение, и клиент собирает своё. Если после подстановки `{0}` остался, значит аргументов пришло меньше, чем ждёт шаблон, и показывается серверная фраза: половина предложения хуже, чем предложение не на том языке.

## Сессия

С 0.21.0 сессия — это токен. Вход отвечает `{user, token}`; клиент хранит токен в DataStore отдельно для каждого сервера и шлёт его в каждом запросе, кроме публичных, как `Authorization: Bearer <token>`. Сервер хранит только SHA-256 токена, держит его 30 дней и продлевает при каждом использовании. При запуске клиент возвращается к сохранённому токену через `GET /api/v1/user/me`; 401 означает, что токена больше нет — клиент его забывает и, если играли по устройству, молча входит снова. Пароль и токен ходят только в теле запроса или в заголовке, никогда в строке запроса; в журнале тело и ответ входа, смены пароля и входа по устройству заменены на `[скрыто]`, заголовок в журнал не пишется вовсе.

| Операция | Запрос |
|---|---|
| Вход | `POST /api/v1/user/login`, тело `{login,password}` → `{user,token}` |
| **Вход по устройству** | `POST /api/v1/user/login/byDeviceId`, тело `{deviceId}` → `{user,token}`, `US_015` если такого устройства нет |
| **Регистрация по устройству** | `POST /api/v1/user/byDeviceId`, тело `{deviceId}` → `{user,token}`, `US_013` если устройство уже заведено |
| Текущий пользователь | `GET /api/v1/user/me` |
| Выход | `POST /api/v1/user/logout` — гасит токен запроса |
| Смена пароля | `POST /api/v1/user/changePassword`, тело `{password,newPassword}` — гасит все остальные сессии аккаунта, текущая остаётся |
| Возможности | `GET /system/routes` → `[{path,method}]`, метод печатается селектором Ktor как `(GET)` |
| Здоровье | `GET /system/health` |
| Версия | `GET /system/version` → `{version}` |

Без токена открыто только это: вход и регистрация, `/locale/*`, `/icons/*` и `/system/{routes,health,version}`. Остальное требует входа, а часть — роли `ADMIN` (`AUTH_003`, 403): выдача предметов и опыта из ничего, `/system/*`, поиск пользователей и **любая** запись через общий CRUD, кроме создания и удаления своего персонажа. Коллекции с чужими данными (`user`, `character`, `characterequipment`, `auctionlot`, `redemptioncodes`, `blocklist`) целиком читает только администратор; игрок читает своё через игровые маршруты и своего персонажа — `GET /api/v1/character?id=`. Чужой `userId` в запросе — `AUTH_005`, чужой `characterId` — `AUTH_004` (оба 403); без токена — `AUTH_001`, с неизвестным или истёкшим — `AUTH_002` (оба 401). Персонаж, созданный игроком, сервер всегда начинает с первого уровня и пустым, что бы ни пришло в теле.

Вход по устройству — это и есть регистрация: сервер держит одну учётную запись на `device_id`, и отказ `US_015` означает «такого устройства ещё не было», а не ошибку. Клиент превращает его в `POST`, который заводит запись и отвечает ею же. Пароля в этом пути нет, а идентификатор устройства — не секрет, а имя; скрыт в журнале этот обмен только потому, что в ответе приходит токен. `device_id` сервер с 0.21.0 в ответах не отдаёт.

Учётная запись, заведённая по устройству, приходит с пустыми `name` и `login` — сервер их не заполняет. Клиент показывает её как «Гость · …хвост идентификатора».

Роль берётся из ответа (`role: USER | MODERATOR | ADMIN`), а не из клиентского состояния. `ApiCapabilities` строится из таблицы маршрутов сервера: перед входом клиент проверяет, что нужные ему пути существуют, и называет отсутствующие.

## Локализация: текста в базе больше нет

С 0.14.0 ни один документ Mongo не хранит текста. Сущность хранит **код**, а строки лежат в статических файлах сервера и отдаются без обёртки `{success,data}` и без учётной записи — язык должен читаться до входа.

С 0.22.0 языков два — `en` и `ru` (китайский убран), и **имя предмета одно на оба**: `equipment.<CODE>.name`, `item.<CODE>.name` и `enum.EnumCurrencyOrb.*` в русском словаре хранят ту же английскую строку, что и в английском, — как в PoE, где вещь ищут и продают под одним именем. Описания, модификаторы, классы, узлы дерева, характеристики и ошибки переводятся. Клиент ничего для этого не делает: он по-прежнему берёт имя из словаря выбранного языка, а свою таблицу названий сфер (`enum.orb.<ORB>`) держит так же английской. С 0.25.0 сервер хранит эти имена один раз, в `locale/common.json`, и отдаёт каждый язык склейкой общего и языкового файла; отпечаток в манифесте считается от склейки, так что для клиента формат не изменился.

| Операция | Запрос |
|---|---|
| Список языков | `GET /locale/index.json` → `{default, languages:[{code,label,hash}]}` |
| Словарь | `GET /locale/{code}.json` → плоская таблица `ключ → строка` |

Ключ строится одинаково на обеих сторонах: `<секция>.<КОД>.<поле>`. Секции: `equipment`, `item`, `modifier`, `skilltree`, `class`, `enum`, `error`, `currency`, `system`. Поля — `name` и `description`; у `enum`, `error`, `currency` и `system` ключ двухчастный (`error.AU_002`, `enum.EnumRarity.RARE`).

`hash` из манифеста — отпечаток словаря: клиент хранит скачанный файл вместе с ним (в разрезе сервера и языка) и перекачивает только при расхождении. Без словаря экран показывает коды, а не пустоту: отсутствующий ключ возвращает сам себя.

Текст модификатора — **шаблон** с `{0}`, `{1}` по числу эффектов: составной модификатор нельзя собрать, приклеив числа к названию, потому что порядок слов в языках разный. Аргументы сообщения о сфере (`messageArgs`) — **сами ключи локализации**, поэтому подстановка идёт через тот же словарь.

Ошибки тоже лежат в словаре (`error.<errorCode>`), но конверт ошибки несёт только готовое предложение и код — аргументов, которыми шаблон был заполнен, в нём нет. Поэтому клиент переводит отказ, только если у шаблона нет дырок (17 кодов из 114); в остальных случаях показывается предложение сервера.

Перечисления (`enum.*`) сервер тоже отдаёт, но клиент оставляет **свои** таблицы слотов, редкостей и статов: они принимают язык параметром, а словарь отвечает на том, который загружен. Сервер владеет названиями вещей, клиент — своими подписями.

Словарь загружен ровно один — кроме аукциона. С 2.2.0 клиент держит рядом английский (`serverLocaleEn`) и печатает в строке лота оба названия: лот сверяют с вики и торговыми площадками, а они английские. Это единственный второй словарь, читает его только витрина, и при английском интерфейсе это тот же самый объект — второй раз ничего не качается. Качается он теми же правилами, что и первый: по отпечатку из манифеста и в тот же кэш, в разрезе сервера и языка.

## Иконки: контуры, а не картинки

С 0.15.0 сервер отдаёт ещё и рисунки. Механика та же, что у словарей, но манифест собирает сам сервер.

| Операция | Запрос |
|---|---|
| Отпечаток набора | `GET /icons/index.json` → `{hash, file, sprites, icons}` |
| Набор | `GET /icons/icons.json` → `{sprites:{…}, icons:{…}}` |

`hash` считается сервером из самого файла при старте, а не лежит в манифесте руками, как у словарей. Руками его можно забыть обновить, и ломается это незаметно: иконку поправили, а клиенты о ней никогда не узнают.

Тело состоит из двух частей. `sprites` — рисунки: `{"helmet":{"viewBox":24,"paths":[{"d":"M4 11…","alpha":1.0}]}}`. `icons` — таблица `код → имя рисунка`: `{"equipment.IRON_SKULLCAP":"helmet"}`. Они разделены, потому что один рисунок обслуживает много кодов — все шлемы берут `helmet`, — а выдать отдельному предмету свой можно правкой одной строки.

Ключи повторяют разделы `LocaleKey`: `equipment.<КОД>`, `item.<КОД>`, `stat.<СТАТ>`. Один код отвечает сразу на два вопроса: как вещь называется и чем рисуется. Модификаторов здесь нет намеренно — у них текст с подстановками, и иконка строку не заменит.

Цвета в рисунке нет, есть только `alpha`. Клиент красит иконку редкостью предмета, как красит свои: цвет, выбранный сервером, дрался бы с тёмной темой, в которую иконка попадает.

Поле `image` — URL картинки у предметов и экипировки — убрано в 0.15.1: его не заполняли сидеры, не читал сервер и не открывал клиент. Миграции оно не требует, лишний ключ в уже сохранённом документе кодек игнорирует при чтении и отбрасывает при записи; клиент старой версии, приславший `image` в PUT, будет молча проигнорирован. Общего редактируемого поля у `items` и `equipment` после этого не осталось: у первых редактируются `category`, `subCategory`, `price`, у вторых — слот, редкость, уровень, требования и пул модификаторов.

Картинок по-прежнему не скачивается: приезжают path-данные, и рисует их клиент. Код, которого в таблице нет, и рисунок, чьи path-данные не разобрались, откатываются к встроенной эмблеме — поэтому опечатка в одном рисунке стоит ровно одной иконки.

## Коллекции

Каждая сущность обслуживается одинаковым набором маршрутов, имя сегмента — имя класса сервера в нижнем регистре: `user`, `character`, `characterequipment`, `items`, `equipment`, `recipe`, `redemptioncodes`, `modifierdefinition`, `modifiertier`, `characterclass`, `experiencelevel`, `skilltreenode`, `auctionlot`.

| Операция | Запрос |
|---|---|
| Вся коллекция | `GET /api/v1/{collection}` |
| Страница | `GET /api/v1/{collection}/paged?page=0&size=20` — **не используется, см. ниже** |
| По ID | `GET /api/v1/{collection}?id=<24 hex>` |
| Количество | `GET /api/v1/{collection}/count` |
| Создание | `POST /api/v1/{collection}`, тело — JSON-**массив** документов |
| Изменение | `PUT /api/v1/{collection}?id=…`, тело — объект только изменённых полей |
| Удаление | `DELETE /api/v1/{collection}?id=…`, без тела |

Версию определяет сервер: он читает документ, сравнивает его `version` в фильтре обновления и отклоняет гонку ошибкой. Клиент не присылает `expectedVersion` и **никогда** не повторяет запись автоматически. Служебные поля (`_id`, `id`, `version`, `deleted`, `createdAt`, `updatedAt`) сервер игнорирует в PUT, клиент их не отправляет. Дискриминатор `type` допустим только при создании экипировки.

`/paged` починен в 0.13.1: `findPaged` считает страницы, а не документы. Но фильтра у общего маршрута по-прежнему нет, и перевод каталога на него стоил бы всех фильтров каталога — слота, редкости, уровня, модификатора в пуле. Поэтому каталог по-прежнему читает коллекцию целиком (`GET /api/v1/{collection}`) и режет её у себя; коллекции небольшие и сеются сервером.

Исключение — аукцион: у него есть собственный `GET /api/v1/auctionlot/search` с фильтром и страницей, и это единственный список в приложении, который сужает сам сервер.

## Экипировка

`Equipment` — sealed-класс с дискриминатором `type`, равным полному имени класса: `features.data.equipment.equipment_data.Weapon | Armor | Accessory`.

```json
{"type":"features.data.equipment.equipment_data.Weapon","code":"IRON_SKULLCAP","slot":"WEAPON_1H","rarity":"RARE",
 "itemLevel":30,"weaponType":"SWORD","damage_min":10.0,"damage_max":20.0,"attackSpeed":1.2,
 "durability":100,"modifierIds":["<ModifierDefinition._id>"]}
```

Редкости: `COMMON, UNCOMMON, RARE, EPIC, UNIQUE, MYTHICAL`. Слоты: `HELMET, BODY, GLOVES, RING, BOOTS, WINGS, BELT, WEAPON_1H, WEAPON_2H, QUIVER, SHIELD, AMULET, JEWEL`. Цену считает сервер в конструкторе — клиент её не пишет.

С 0.10.0 у предмета нет собственных числовых полей под характеристики: `damage_min`, `damage_max`, `attackSpeed` у оружия и `defense` у брони убраны. Броня, урон и скорость атаки задаются готовыми модификаторами в `baseParams` — с фиксированными значениями и без тира, потому что база базового типа не роллится. Единственное число, оставшееся полем предмета, — `durability` у оружия: это не характеристика персонажа.

Требования `requiredLevel`, `requiredStrength`, `requiredDexterity`, `requiredIntelligence` сервер проверяет дважды, и это два разных правила:

- `POST /api/v1/characterequipment/equip` **отказывает**, если требования не выполнены (`CH_013`, «Equipment requirements are not met»);
- уже надетый предмет при потере требований из слота не слетает — он просто перестаёт учитываться и попадает в `inactive` листа характеристик.

Клиент требования только печатает и никогда не блокирует по ним кнопку сам: команда отправляется, отказ сервера показывается.

`modifierIds` — это **пул ссылок**, а не выпавшие значения. Что попадёт на экземпляр, решает сервер: PREFIX и SUFFIX роллятся в количестве, которое задаёт редкость, а IMPLICIT, ENCHANTMENT, CORRUPTION и UNIQUE попадают на каждую копию.

С 0.16.0 `baseParams` **не копируются** на экземпляр. База — броня, урон, скорость атаки, требования — живёт в справочнике в единственном экземпляре, и экземпляр приходит к ней по `equipmentId`. Из этого следует три вещи: перебалансировка базы доезжает до всех уже выданных копий сама, карточка перестала печатать одно и то же свойство дважды (раньше `+12 к броне` приезжало и из шаблона, и из копии), а справочник стал обязательным для отрисовки. Клиент читает `GET /api/v1/equipment` целиком один раз за сессию (`ForgeRuntime.ensureEquipment`), и маршрут назван в `requireWorkbench`: на устаревшем сервере будет сказано, чего не хватает, а не нарисована половина предмета.

Слот `JEWEL` — самоцвет. Это обычный документ экипировки со своим пулом модификаторов, но носят его не на теле, а в гнезде дерева навыков (см. «Дерево навыков»). Уникальных самоцветов сервер не сидит.

Весь справочник экипировки, предметов и валюты сервер с 0.16.0 читает из JSON-ресурсов — `resources/content/{equipment,items,currency}.json`, — а не собирает в коде. Уникальные предметы остались в Kotlin: каждый порождает собственные `ModifierDefinition` с диапазонами тиров, и это уже не данные, а правила.

## Инвентарь персонажа

Продажа торговцу (`characterequipment/sell`, 0.17.0) уничтожает экземпляр и платит золотом. Цену считает сервер: базовая цена шаблона × множитель редкости × число выпавших аффиксов × `STOCK_GOLD` персонажа. Последний множитель — задел: характеристика в перечислении есть, её пока никто не выдаёт, и пока она равна нулю цена от неё не меняется; появится модификатор «увеличение стоимости продажи» — заработает сам. Надетое (`CH_014`) и вставленное в гнездо (`CH_015`) не продаётся, как и не выставляется на аукцион. Ответ говорит, сколько дали и сколько золота стало.

Экземпляр предмета — отдельный документ коллекции `CharacterEquipment`: `{_id, characterId, equipmentId, params, rarity, corrupted, mirrored, equippedSlot, socketCode, version}`. `equippedSlot = null` означает «лежит в инвентаре»; слот задаёт шаблон, поэтому клиент его не выбирает. `socketCode` с 0.16.0 говорит, в каком гнезде дерева сидит самоцвет: слот отвечает, *что* это за вещь, а код — *где* она надета, и поэтому одного `equippedSlot` мало (гнёзд много, и каждое можно занять).

`rarity` с 0.9.1 принадлежит копии, а не шаблону: шаблон задаёт лишь то, с чем предмет падает, дальше редкость двигают сферы. `corrupted = true` закрывает предмет навсегда — сервер отклонит на нём любую следующую сферу; `mirrored = true` с 0.20.0 делает то же самое (`CR_010`), но это другое состояние: копия, снятая зеркалом, Ваал не видела. Клиент не перечисляет состояния списком — `itemStates` читает с документа всё булево со значением `true`, поэтому новый флаг сервера появляется на карточке сам. В карточке инвентаря редкость экземпляра перекрывает редкость шаблона.

| Операция | Запрос |
|---|---|
| **Персонажи игрока** | `GET /api/v1/character/byUser?userId=` → `[Character]`, `CH_004` если такого игрока нет |
| Весь инвентарь | `GET /api/v1/character/inventory/equipments?characterId=` |
| Только надетое | `GET /api/v1/character/inventory/equipped?characterId=` |
| Характеристики | `GET /api/v1/character/inventory/stats?characterId=` → `CharacterStats` (см. ниже) |
| **Продать торговцу** | `POST /api/v1/characterequipment/sell?characterId=&inventoryId=` → `{inventoryId, code, gold, money}` |
| Начислить опыт | `POST /api/v1/character/inventory/experience?characterId=&amount=` → документ персонажа |
| Простые предметы | `GET /api/v1/character/inventory/items?characterId=` → `[{itemId,amount}]` |
| Изменить сумку | `POST /api/v1/character/inventory/addItem?characterId=`, тело `[{itemId,amount}]` |
| **Выдать предмет с роллами** | `POST /api/v1/character/inventory/itemToInventory?characterId=&equipmentId=` |
| **Применить сферу** | `POST /api/v1/characterequipment/applyOrb?characterId=&inventoryId=&orbItemId=` |
| Надеть | `POST /api/v1/characterequipment/equip?characterId=&inventoryId=[&slot=RING\|RING_2]` |
| Снять | `POST /api/v1/characterequipment/unequip?characterId=&inventoryId=` |
| **Вставить самоцвет** | `POST /api/v1/characterequipment/socket?characterId=&inventoryId=&nodeCode=` → экземпляр |
| **Вынуть самоцвет** | `POST /api/v1/characterequipment/unsocket?characterId=&inventoryId=` → экземпляр |
| Рецепт | `POST /api/v1/recipe/useRecipe?characterId=&recipeId=`, тело `{ingridientsId,amount}` |
| Промокод | `POST /api/v1/redemptioncodes/useRedeptionCode?characterId=&redemptionCode=` |

Часть команд — POST с аргументами в строке запроса и без тела; клиент отправляет пустое тело, потому что этого требует HTTP-клиент, а не сервер.

С 0.24.0 надевание снимает и то, с чем предмет не носится: двуручное оружие освобождает `WEAPON_1H`, `SHIELD` и `QUIVER`; лук (одноручный) носится с колчаном, любое другое одноручное — со щитом. Колец два: второе надето в `equippedSlot = RING_2` — шаблона с таким слотом не бывает. Без `slot` кольцо занимает свободное место, а если заняты оба — первое. Обычные базы теперь есть во всех слотах (223 базы PoE), у каждого слота свой пул модификаторов, а локальные аффиксы защиты и урона определяет сама база.

## Класс, уровни и расчёт характеристик

`stockSkills` и `params` у персонажа убраны. Вместо них персонаж ссылается на класс полем `classId` — обязательным при создании и неизменяемым потом: базу класса читают при каждом расчёте, и перенос персонажа в другой класс молча переписал бы его историю. Маршрута для такой правки у сервера нет.

```json
// characterclass
{"_id":"…","code":"MARAUDER","name":"Marauder","startNodeCode":"STR_START",
 "baseStats":[{"stat":"STOCK_STRENGTH","value":32.0}],
 "perLevelStats":[{"stat":"STOCK_HEALTH","value":12.0}],
 "params":[{"modifierId":"…","values":[1.0]}]}
// experiencelevel
{"_id":"…","level":3,"experience":300.0,"skillPoints":2}
```

Ответ `stats`:

```json
{"characterId":"…","level":12,"stats":{"STOCK_HEALTH":188.4,…},
 "active":["<CharacterEquipment._id>"],
 "inactive":[{"inventoryId":"…","code":"IRON_SKULLCAP","reasons":["strength: need 30, have 14"]}],
 "unwearable":[{"equipmentId":"…","code":"TOWER_SHIELD","reasons":["strength: need 60, have 14"]}]}
```

Считается в два прохода: сначала база класса на уровне персонажа плюс дерево навыков, затем экипировка в порядке слотов — каждый следующий предмет проверяется по характеристикам, которые уже дали база, дерево и признанные рабочими предметы. Предмет, чьи требования не выполнены, остаётся в слоте, но не работает и попадает в `inactive` со своей причиной. Клиент печатает и числа, и причины; ни того, ни другого он не вычисляет.

`unwearable` добавлено в 0.17.0: это вердикт по **всему справочнику экипировки** — какие шаблоны персонаж сейчас надеть не может и почему. Требование лежит на шаблоне, а не на экземпляре, поэтому один ответ помечает и арсенал, и чужой лот на витрине, а клиенту остаётся посмотреть, есть ли шаблон в списке, — сверять требования сам он по-прежнему не должен.

У эффекта модификатора есть `perStat` и `perAmount`: это конверсия вида «+1 к здоровью за каждые 2 Силы». Неполный шаг не засчитывается. Порядок статов на сервере запрещает циклы конверсий — клиент на это не опирается. Флаг `isLocal` у описания говорит, что модификатор сворачивается внутри своего предмета, а наружу отдаёт результат.

**Конверсии класса до 0.17.0 не применялись вовсе.** Они лежат в `CharacterClass.params` — пять общих, от «Силы в здоровье» до «Интеллекта в щит», — но расчёт разворачивал дерево и экипировку и никогда не разворачивал класс, так что Сила и Интеллект не давали ничего. Теперь они разворачиваются в том же проходе, что и дерево, то есть до экипировки; именно это и позволяет атрибуту с надетого предмета кормить конверсию — калькулятор считает статы в порядке `order`, и источник посчитан раньше приёмника.

## Дерево навыков

Общее дерево — справочник `skilltreenode`. Прокачка персонажа с 0.12.1 лежит **внутри документа персонажа**, в поле `skillNodes`: отдельной коллекции у взятых узлов нет.

```json
// skilltreenode
{"_id":"…","code":"STR_LIFE_1","name":"Крепость","type":"NOTABLE","cost":1,
 "connections":["STR_START"],"positionX":-20,"positionY":10,
 "params":[{"modifierId":"…","values":[10.0]}]}
```

Виды узлов: `START, SMALL, NOTABLE, KEYSTONE, JEWEL_SOCKET`. Связи двусторонние и записаны в обоих концах. Координаты нужны только для отрисовки.

С 0.16.0 дерево — это файл, `resources/skilltree/tree.json`: 299 узлов (7 стартовых, 246 малых, 30 значимых, 10 гнёзд, 6 ключевых) и 423 связи. `SkillTreeSeeder` его только читает и проверяет на дубликаты кодов и на связи в никуда. Общего кольца нет: семь областей классов сходятся собственными ветками, поэтому пройти через чужой стартовый узел нельзя, а Скион добирается до всех областей из центра.

| Операция | Запрос |
|---|---|
| Дерево персонажа | `GET /api/v1/character/skilltree/state?characterId=` → `CharacterSkillTreeState` |
| Взять узел | `POST /api/v1/character/skilltree/allocate?characterId=&nodeCode=` |
| Вернуть узел | `POST /api/v1/character/skilltree/refund?characterId=&nodeCode=` |
| Сбросить дерево | `POST /api/v1/character/skilltree/reset?characterId=` |

Все четыре отвечают состоянием целиком: `{characterId, total, spent, available, nodes, totals}`.

`totals` — это **вклад дерева**, список строк вида `{stat, operation, value}`, по строке на характеристику и вид операции. ADD и INCREASED складываются, MORE перемножаются в один честный процент, SET оставляет последний. Базы под ним нет и быть не должно: это то, что даёт дерево, а не итог персонажа, поэтому «+40% к физическому урону» остаётся процентом.

До 0.17.0 здесь лежал итог, посчитанный от **пустой** базы, и это молча ломало половину ответа: `0 × 1.4 = 0`, а ноль отбрасывался, так что ни один процентный узел в «Подробно» не показывался — видно было только ADD. Взятый узел — снимок `{code, params, name, type, cost, description}` без собственного `_id`. Очки даёт таблица уровней. Стартовый узел класса **выдаётся при создании персонажа** и стоит ноль очков, поэтому дерево нового персонажа не пустое. Сброс — это респек: он оставляет персонажа на стартовом узле, а не обнуляет дерево. Дальше берут только соседей уже взятых; вернуть узел можно, только если остальное дерево не повиснет, а стартовый — лишь полным сбросом. Форма дерева намеренно не копируется: связи и координаты берутся из актуального справочника. Все эти правила проверяет сервер; клиент называет код узла и показывает отказ.

Возврат перестал быть бесплатным. Один возвращённый узел стоит одну **сферу сожаления** (`ORB_OF_REGRET`), полный сброс — по сфере за каждый возвращаемый узел; не хватило — `ST_015`. Сфера списывается из сумки той же командой, отдельного запроса нет. Клиент спрашивает подтверждение перед каждой из трёх команд и называет в вопросе цену.

Узел `JEWEL_SOCKET` сам ничего не даёт: взяв его, персонаж открывает гнездо. В гнездо вставляют самоцвет — обычный экземпляр экипировки со слотом `JEWEL` — командой `POST /api/v1/characterequipment/socket`, назвав код узла. Модификаторы самоцвета действуют **глобально**, пока гнездо взято: `CharacterStatsCalculator` пропускает самоцвет, чьё гнездо не в `skillNodes`. Занятое гнездо вернуть нельзя — сервер отказывает (`ST_014`), а не роняет самоцвет молча; сначала `unsocket`. Прочие отказы: `ST_016` — узел не гнездо, `ST_017` — предмет не самоцвет, `CR_009` — сфера не для этого предмета.

## Аукцион

Коллекция `auctionlot`. Открывается с уровня, который задаёт константа сервера (`CONST_AUCTION_MIN_LEVEL`), и порог стоит на **всех** маршрутах, включая просмотр витрины: отказ `AU_002`. Клиент копии этого числа не держит и узнаёт порог только из отказа.

`createdAt` — момент выставления, записанный сервером в **UTC**: его `LocalDateTime.now()` это `Clock.System.now().toLocalDateTime(TimeZone.UTC)`, поэтому своей зоны в отметке нет и клиент показывает её в зоне устройства.

Пока лот на витрине, товар лежит **внутри него**, а не у продавца: экземпляр экипировки уходит из `CharacterEquipment` прямо в лот, стаки списываются со склада. Поэтому выставить предмет дважды или надеть выставленный нельзя, а надетый не выставить вовсе (`AU_010` — сначала снять).

```json
{"_id":"…","sellerId":"…","sellerName":"Изгнанник","kind":"EQUIPMENT|ITEM",
 "equipment":{…CharacterEquipment…},"itemId":"","amount":1,
 "priceOrbId":"<Items._id категории CURRENCY>","price":40,
 "itemCode":"IRON_SKULLCAP","slot":"HELMET","rarity":"RARE","itemLevel":30,
 "createdAt":"2026-09-22T10:15:30","status":"ACTIVE|SOLD|CANCELLED","buyerId":null}
```

| Операция | Запрос |
|---|---|
| Витрина | `GET /api/v1/auctionlot/search?characterId=&page=&size=` + поля фильтра |
| Свои лоты | `GET /api/v1/auctionlot/my?characterId=` — и активные, и закрытые |
| Выставить экипировку | `POST /api/v1/auctionlot/sell/equipment?characterId=&inventoryId=&priceOrbId=&price=` |
| Выставить предметы | `POST /api/v1/auctionlot/sell/item?characterId=&itemId=&amount=&priceOrbId=&price=` |
| Купить | `POST /api/v1/auctionlot/buy?characterId=&lotId=` |
| Снять с продажи | `POST /api/v1/auctionlot/cancel?characterId=&lotId=` |

Поля фильтра: `kind`, `title`, `slot`, `rarity`, `minItemLevel`, `maxItemLevel`, `priceOrbId`, `maxPrice`, `sellerId`, `excludeSellerId`, `lang`. Названия в лоте нет — есть `itemCode`, поэтому поиск по тексту сервер превращает в поиск по кодам, и `lang` говорит, на каком языке игрок набрал запрос; клиент шлёт его только вместе с непустым `title`. Пропущенное поле — «не фильтровать», а **незнакомое значение перечисления сервер отклоняет**, поэтому клиент не отправляет пустые поля вовсе. Поиск по названию экранирует спецсимволы: игрок присылает текст, а не регулярное выражение. Закрытые лоты на витрине не показываются никогда.

Цена назначается **только в сферах**: `priceOrbId` обязан быть предметом категории `CURRENCY`, иначе лот не выставится (`AU_007`). Оплата, передача товара и закрытие лота идут одной транзакцией, поэтому нехватка сфер не оставляет ни списанных денег, ни потерянного предмета. Свой лот купить нельзя (`AU_006`). Снятие возвращает товар продавцу; закрытые лоты остаются историей торгов.

Все поля витрины (`itemCode`, `slot`, `rarity`, `itemLevel`) — снимок предмета на момент выставления, поэтому поиск укладывается в один запрос. Редкость берётся с экземпляра, а не с шаблона: её могли изменить сферы.

### Персонажи одного игрока

`GET /api/v1/character/byUser?userId=` — список целиком, без страниц: больше `CONST_USER_MAX_CHARACTERS` (три) персонажей у игрока не бывает, и четвёртый отклоняется `CH_005`. Это единственный список персонажей, который читает клиент: экран выбора при входе. Коллекцию целиком он не вычитывает — чужие персонажи за пределы сервера не уезжают. Неизвестный `userId` отклоняется `CH_004`, а не пустым списком, иначе опечатка выглядела бы как игрок без персонажей.

Создание персонажа — `POST /api/v1/character` с документом из трёх полей: `userId`, `name`, `classId`. Больше клиент не шлёт ничего: уровень, деньги, сумка, взятые узлы и все списки навыков — серверные, и он проставляет их сам. Шаблон формы редактора (`template(Catalog.CHARACTERS)`) рисует поля целиком и payload'ом не является; `api.catalog.create` отклоняет лишнее до запроса и называет поля поимённо.

## Валютные сферы

Сфера — обычный предмет коллекции `items` с категорией `CURRENCY`; подкатегория равна имени элемента серверного `EnumCurrencyOrb` и связывает документ с его поведением. Отдельной коллекции и отдельного маршрута каталога у сфер нет: клиент читает `GET /api/v1/items` и отбирает эту категорию.

```json
{"_id":"…","code":"CHAOS_ORB","category":"CURRENCY","subCategory":"CHAOS_ORB","price":300}
```

Название и описание — в словаре под `item.<CODE>.name` и `item.<CODE>.description`.

Сервер реализует восемнадцать сфер: `ORB_OF_TRANSMUTATION, ORB_OF_AUGMENTATION, ORB_OF_ALTERATION, ORB_OF_ALCHEMY, REGAL_ORB, CHAOS_ORB, EXALTED_ORB, DIVINE_ORB, ORB_OF_ANNULMENT, ORB_OF_SCOURING, BLESSED_ORB, VAAL_ORB, ORB_OF_CHANCE, MIRROR_OF_KALANDRA, FRACTURING_ORB, SHAPERS_ORB, ELDER_ORB, ORB_OF_REGRET`. Последняя добавлена в 0.16.0 и стоит особняком: на предмет её не применяют (`CR_009`), её тратит дерево навыков за возврат узла. Сфер POE, завязанных на сокеты, качество и карты, здесь нет.

С 0.23.0:

- **Fracturing Orb** закрепляет случайный аффикс редкого предмета с четырьмя аффиксами и больше: у выпавшего модификатора появляется `"fractured": true`, и его больше не снимают Annulment и Scouring, не перекатывают Chaos, Alteration и Divine. Скоуринг такого предмета оставляет его магическим, потому что обычный аффиксов не держит. Отказы: `CR_011` (уже есть закреплённый), `CR_012` (меньше четырёх аффиксов).
- **Shaper's Orb** и **Elder Orb** ставят на экземпляр `"influence": "SHAPER" | "ELDER"` и добавляют модификатор из пула этого влияния; дальше этот пул открыт и остальным сферам. Нужны редкий предмет, свободное место (`CR_007`) и отсутствие влияния (`CR_014`); самоцвет влиянию не поддаётся (`CR_013`).

`POST /api/v1/characterequipment/applyOrb?characterId=&inventoryId=&orbItemId=` отвечает:

```json
{"messageKey":"currency.chaos","messageArgs":["equipment.IRON_SKULLCAP.name","4"],
 "item":{…CharacterEquipment…},"created":null}
```

Текста здесь нет: фразу собирает клиент по `messageKey` и `messageArgs`, причём **аргументы — тоже ключи локализации**, поэтому предмет называется через тот же словарь.

Всё решает сервер: какую редкость сфера требует, сколько аффиксов роллит, какие оставляет. Сфера списывается из сумки персонажа в той же транзакции, поэтому отказ (`errorCode` семейства `CR_00…`) ничего не стоит. `created` заполняет только `MIRROR_OF_KALANDRA` — это созданная копия, и она сразу `mirrored` (до 0.20.0 — `corrupted`). Клиент печатает собранную фразу как есть и не выводит результат сам.

Редкость задаёт вместимость аффиксов: `COMMON 0`, `UNCOMMON 1+1`, `RARE 3+3`, `EPIC 4+3`, `MYTHICAL 4+4`, `UNIQUE` не роллит аффиксов вовсе. Это правило сервера — клиент на него не опирается и ничего по нему не считает.

## Модификаторы

Описание и его диапазоны разнесены по двум коллекциям.

```json
// modifierdefinition
{"_id":"…","code":"LIFE_AND_MANA","source":"PREFIX","tags":["life"],
 "effects":[{"stat":"STOCK_HEALTH","operation":"ADD"},{"stat":"STOCK_MANA","operation":"ADD"}]}
// modifiertier
{"_id":"…","modifierId":"…","tier":1,"minItemLevel":84,"weight":100,
 "values":[{"valueMin":46.0,"valueMax":48.0},{"valueMin":10.0,"valueMax":12.0}]}
```

С 0.23.0 у определения ещё четыре поля: `group` (на одном предмете не бывает двух модификаторов одной группы; `null` — группа равна коду), `spawnWeight` (вес во взвешенном выборе аффикса), `influence` (`SHAPER`/`ELDER` — модификатор роллится только на предмете с этим влиянием) и `crafted` (модификатор верстака: сферы его не роллят). Клиент читает их только для показа.

Текста у определения нет: строка лежит в словаре под `modifier.<CODE>.name` и является шаблоном с `{0}`, `{1}` по числу эффектов. Составной модификатор меняет несколько статов сразу: у него больше одного эффекта, и на экземпляре ему соответствует столько же значений в том же порядке. Тир 1 — лучший. Выпавший модификатор экземпляра: `{modifierId, tierId, tier, values:[Double], fractured}`.

### Верстак (с 0.23.0)

`GET /api/v1/characterequipment/bench` — строки верстака, неизменные для сервера:

```json
[{"code":"CRAFTED_ADD_MAXIMUM_LIFE_T3","modifierId":"…","modifierCode":"CRAFTED_ADD_MAXIMUM_LIFE","tierId":"…","tier":3,
  "source":"PREFIX","group":"ADD_MAXIMUM_LIFE","values":[{"valueMin":25.0,"valueMax":34.0}],
  "orb":"ORB_OF_TRANSMUTATION","orbItemId":"…","amount":3,"slots":[]}]
```

`POST /api/v1/characterequipment/craft?characterId=&inventoryId=&recipe=<code>` ставит ремесленный модификатор выбранного тира (значение внутри тира роллит сервер), `POST /api/v1/characterequipment/uncraft?characterId=&inventoryId=` снимает его за Orb of Scouring. Оба отвечают как `applyOrb`: `{messageKey, messageArgs, item}`. Правила сервера: предмет магический или выше, ремесленный модификатор на предмете один (`CR_015`), встаёт на свободное место своего вида (`CR_007`) и не рядом с модификатором своей группы (`CR_016`), строка подходит слоту (`CR_019`); снимать нечего — `CR_017`, строки нет — `CR_018`. Сферы списываются в той же транзакции, отказ ничего не стоит.

Дополнительно: `GET /api/v1/modifierdefinition/byCode?code=`, `GET /api/v1/modifiertier/byModifier?modifierId=`, `GET /api/v1/{collection}/cache/hash` для кэшируемых коллекций.

## Чего у этого сервера нет

Боя, JWT, поиска и фильтров на сервере, курсорной постраничной выдачи инвентаря. Соответствующие экраны и модели из клиента удалены, а не заглушены. Сферы вернулись в 0.9.1, дерево навыков — в 0.9.2; и то и другое реализовано целиком.

## Совместимость

Формат данных игроков с тех пор менялся несколько раз (класс и дерево у персонажа, база предмета модификаторами), поэтому базу, пережившую 0.9.x, проще пересеять с нуля, чем чинить. В 0.14.0 из документов убраны `name` и `description` — база без кодов не читается вовсе.
