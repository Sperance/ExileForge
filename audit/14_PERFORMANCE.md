## [PERF-01] Каждый ответ команды кодирует и хеширует всего героя
- **Категория:** PERFORMANCE. **Приоритет:** P3. **Уверенность:** высокая (код), средняя (оценка нагрузки).
- **Подсистема:** сервер, `HeroSnapshots`.
- **Файлы:** `src/main/kotlin/.../features/logic/hero/HeroSnapshots.kt:157-178` (`of(heroId)`: `requireHero` если не `WrittenHero`, `reconcileShown` → возможный `save`, `crafts.settle`, затем `of(hero, known)`), `:168-178` (каждая часть: `encodeToJsonElement` + `sha256(json.toString())`).
- **Инвариант:** нет прямого; RULES «Сервер работает одной копией» — CPU одного процесса общий.
- **Факт:** чтобы решить, какие части не слать, сервер кодирует **все** части (16 корзин вещей, порядок, сумку, дерево, кампанию, ремёсла, торговца) и считает SHA-256 каждой — на каждый POST с `heroId`, включая каждую пачку журнала захода. Замер: 3–7 мс CPU на вещи при 500–1100 копиях (плюс прочие части). Отправляется обычно 1–3 части.
- **Последствия:** при N активных героях с полным тайником и журналом раз в ≤20 с — ~0.4 мс CPU/с на героя только на снимки; на 1000 одновременных — ~0.4 ядра. Сейчас не узкое место.
- **Варианты:** (1) кешировать отпечатки частей в памяти по `version` героя и грязным полям (`BaseRepository` уже знает изменённые поля — `derive`/`unchanged`); (2) хешировать корзину по версиям вещей, а не по JSON.
- **Регрессионный тест:** не нужен; при правке — тест «одинаковый снимок до и после кеша».
- **Статус:** открыто (низкий приоритет).

## [PERF-02] Клиент на каждый снимок трижды декодирует все вещи и пересчитывает лист
- **Категория:** PERFORMANCE. **Приоритет:** P3. **Уверенность:** высокая (код); время на Android не измерено.
- **Подсистема:** `app/presentation/hero/HeroSync.kt`, `core/model/sync/Sync.kt`.
- **Файлы:** `Sync.kt:137-142` — `HeroParts.items`/`hero` — геттеры без кеша, каждый раз декодируют все 16 корзин; `HeroSync.kt:121-157` — `apply()`: `merged.hero` дважды (`earnedBefore`, `info`), `merged.items` трижды (лист, `filter { it.equipped }` для `CombatSheet`, `HeroView`), затем `Sheets.calculate` и `CombatSheet.of(...).figures` — на **каждый** снимок, даже если пришли только `bag` или `campaign` (журнал захода).
- **Факт:** замер JVM: полное декодирование 1100 вещей ≈ 4.4 мс → ×3 ≈ 13 мс + пересчёт листа; на телефоне кратно дольше. Идёт вне главного потока (`Dispatchers.Default`), снимки, обогнанные новыми, отбрасываются — кадр не замерзает, но батарея и задержка отрисовки героя растут с размером тайника.
- **Варианты:** (1) кеш декодированных частей по их `version` в `HeroParts` (`by lazy` или карта version→value); (2) пересчитывать лист, только если сменились `hero`, экипированные вещи или `tree`.
- **Статус:** открыто.

## [PERF-03] 304 на `hero/view` всё равно читает весь документ героя
- **Категория:** PERFORMANCE. **Приоритет:** P3. **Уверенность:** высокая (код).
- **Файлы:** `HeroSnapshots.kt:146-152` (`view`: `heroes.requireHero` — полный документ с вещами и `runs.hydrate`, затем ETag), `HeroRepository.kt:388`.
- **Факт:** ETag сверяется после полного чтения героя (сотни КБ BSON у полного тайника) и гидратации захода. Для ответа 304 нужна только `version`.
- **Варианты:** сначала `find(_id).projection(version)`, полный документ — только при несовпадении.
- **Статус:** открыто.

## [PERF-04] Ответы API не сжимаются сервером
- **Категория:** PERFORMANCE. **Приоритет:** P3. **Уверенность:** средняя — **не проверено** на проде.
- **Факт:** в Ktor нет `Compression`; gzip отдаётся только статике (`Routing.kt:59-78`, `respondStatic`). Полный снимок при 1100 вещах ≈ 340 KB JSON (первый вход, новый телефон, `parts` пусты). Клиент gzip принимает (OkHttp). Конфигурация Caddy (`deploy/update.sh:240` поднимает `caddy`) в репозитории отсутствует — включён ли `encode gzip` на VPS, неизвестно.
- **Варианты:** `install(Compression) { gzip { minimumSize(1024) } }` для JSON или `encode zstd gzip` в Caddy.
- **Вопрос владельцу:** есть ли `encode` в Caddyfile на VPS?
- **Статус:** не проверено.

## 3. Блокировки, кеши, N+1 (проверено кодом выборочно)
- Мутации героя — `HeroLocks.withLock(heroId)` (в памяти) + транзакция; глобальных замков на пути чтения нет. Рост `HeroLocks` и кешей ограничен (`BoundedCache` с `maxSize`/TTL: сессии, владельцы, присутствие 50 000, таблицы славы, торговец, счётчики аукциона).
- Доски славы: верх таблицы — кеш `hallCacheSeconds` (60 с), место героя — отдельный `count` (`HeroRepository.boardPlace`).
- N+1: `HeroRepository.cards/profiles/guildTallies` читают пачкой `Filters.in` — N+1 не найдено в просмотренных местах; `AuctionService.reconcileAll` на старте перебирает все активные лоты по одному (`findByFilter … forEach { reconciled(it) }`, запись — только изменившихся) — разовая стоимость старта.
- Клиент: снимок забега ≤20 раз/с (`HudCadence`), часы декора 30 кадров/с и сон в фоне — по RULES; код не профилировался.
