# CLAUDE.md

Правила выше всего остального. Файл меняет только владелец или по его явной просьбе.

## Начало задачи
- Прочитай `RULES.md`: там инварианты игры, версии, архитектура, CI. `CLAUDE.md` - как работать, `RULES.md` - что обязано быть верно в коде.
- Убедись, что стоишь на рабочей ветке (ниже) и она свежая. Сервер закреплён сабмодулем `backend/` - без него не собирается.

## Общение
- Экономь токены: без промежуточного текста, команд, кода, diff, планов и рассуждений.
- Финальный ответ - одно-два коротких предложения о результате. Что не проверено или не сделано - говори первым, без пересказа задачи и извинений.
- Задача ясна - делай без подтверждений. Неоднозначна - один короткий вопрос с вариантами. Новая механика, баланс или дизайн - спрашивай, если сомневаешься хоть немного.
- Общение по-русски. Код и коммиты по-английски, комментарии и KDoc по-русски.

## Работа
- Читай точечно: grep и фрагменты, не файлы и деревья целиком. Интернет - только когда без него нельзя (зависимости, CI, GitHub); документацию «на всякий случай» не ищи.
- Код уровня Senior Kotlin, с абстракцией. Игровые инварианты и границы модулей - в `RULES.md`, они обязательны.
- Тесты - только критично необходимые. Сборок по ходу работы нет: ни тестов, ни ktlint, ни компиляции после каждой правки или слияния; агенты-исполнители работают каждый в своём worktree и проверяют правку чтением diff. Проверка одна - на сводном коде перед пушем в рабочие ветки: затронутые изменением тесты, `ktlintCheck` и `commentStyle` затронутых модулей, компиляция; остальное проверит CI. Снимков экранов для проверки не делаем.
- Удаляя или переименовывая код, контент или ключ локали - найди grep'ом всех, кто ссылается: локаль, тесты, скрипты, workflow, второй репозиторий.
- «Сгенерируй дизайн» = ровно 3 варианта макета одним HTML-файлом; в репозиторий не коммитить, отдать файлом.

## Git
- Одна рабочая ветка `claude/sharp-bardeen-6i3dkz`; все коммиты только в неё. Новых веток не создавать, в другие не пушить, историю не переписывать, PR без просьбы не открывать.
- Исключение — ветка-черновик `wip` для многошагового пакета с одним финальным пушем: после каждого законченного коммита, даже мелкого, пушить его в `wip` (`git push origin HEAD:refs/heads/wip`), сервер раньше клиента. Workflow на `wip` не запускаются (android.yml — `branches-ignore`, deploy.yml — только рабочая ветка); `versionName` новой версии поднимать только в финальном коммите, который пушится в рабочую ветку. После финального пуша `wip` можно перезаписывать следующим пакетом.
- Папок `docs/` в репозиториях нет и не заводить. Что хранит `audit/` клиента (ExileForge) и как живёт `audit/work/` в `wip` — `backend/RULES.md`, «Общее» → «Версии и релиз».
- Conventional Commits: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `style:`, `ci:`. Форматирование - отдельным `style:`-коммитом, не вперемешку с логикой.

## Отчёты из игры (GitHub Issues)
- Отчёты из игры (предложений нет) - Issues в Sperance/ExileForge с метками `from-game` и `bug` (падения клиента - ещё `crash`, `auto`); репозиторий публичный - в Issue и комментариях ничего личного об игроке.
- «Разбери баги» - прочитай открытые Issues `from-game` (`gh api`, REST), по каждому - вопросы владельцу, если неясно; чини коммитом с «Closes #N» - job `release` закроет его с версией.
- Отказ - сразу закрыть Issue с меткой `wontfix` (или `duplicate`, `invalid`) и комментарием-причиной: игрок его увидит, ему придёт письмо. Комментарии с пометкой «из игры» пишут автор отчёта и модерация - отвечай им в Issue.

## Отчёт об обновлении

- После каждого обновления в финальном ответе и в сообщении каждого коммита указывай, нужно ли обновить сервер и нужен ли вайп сервера. В коммите — трейлеры `Server-Update: yes|no` и `Server-Wipe: yes|no`.
- Изменение сервера ломает форму сохранённых данных - по умолчанию автовайп через `CollectionSchemas` сервера (его `RULES.md`), в ответе - какие коллекции снесутся. Нужна миграция с сохранением данных - скажи владельцу до коммита.

## Завершение изменения
- Подними `versionCode` (+1) и `versionName` (семвер из `RULES.md`) в `app/build.gradle.kts`.
- Перепиши `RELEASE_NOTES.md` заметками только этой версии: заголовок `## <versionName>`, по-русски, для игрока; техническое изменение - одна строка.
- Задача затрагивает сервер - сначала сервер (ktor-bestgame), затем закрепи его здесь: сабмодуль `backend/` и `API_REVISION` (версию и коммит сервера Gradle берёт из сабмодуля).
- Закоммить, запушь, проверь, что `android.yml` зелёный и job `release` опубликовал `v<versionName>`.
