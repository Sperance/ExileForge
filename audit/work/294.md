# #294 Падения в отчётах дублируются и тянутся старые
Пакет: 3 Багрепорты и модерация; статус: в работе; сервер: да (рекомендуется); дизайн: нет
## Разбор
CrashKeeper.kt:48-54 trim KEEP=3 (:96), sent() :76-78 только переименовывает .pending→.sent, recent() :81-83 отдаёт все, в т.ч. отправленные; BugEvidence.kt:23 прикладывает их к каждому BUG. Сервер FeedbackService.kt:77 без склейки; CrashPrint (:79) только для CRASH; IssueFate.kt:142-147 блок «Падения клиента перед отчётом». Файлы не устаревают ни по времени, ни по версии; одинаковые стеки не склеиваются; у падений уже есть свои Issue. В CrashTrace нет времени (только в имени файла).
Предложение: Б — клиент: только текущая версия и ≤24 ч, склейка с «×N»; сервер: склейка по CrashPrint. Тест IssueFateTest.
Попутно: стек 0.16.2 EffectShelf.kt:247 powerFacts /0 — проверить, исправлен ли.
## Вопросы и ответы
1. Какие падения прикладывать: текущей версии за 24 ч (рекомендовал) / этого запуска / не прикладывать / неотправленные. Ответ: текущей версии за 24 ч.
2. Повторы: склеивать с «×N» (рекомендовал) / только первое. Ответ: склеивать с «×N».
3. Сервер: склейка по CrashPrint + «см. #N» на Issue падения (рекомендовал) / только склейка / только клиент. Ответ: склейка + ссылка.
4. Стереть накопленные: да, отправленные (рекомендовал) / нет. Ответ: да.
5. Уточнение (удаление сразу после CRASH противоречит п.1): хранить отправленное 24 ч, потом удалять (рекомендовал) / удалять сразу. Ответ: хранить 24 ч.
## Решение
Клиент CrashKeeper: время падения в CrashTrace (или из имени файла), recent() — только текущей versionName и ≤24 ч, склейка одинаковых стеков с ×N; отправленные (.sent) удаляются старше 24 ч, при обновлении версии — все отправленные прежних версий; неотправленные не трогать. Сервер FeedbackService/IssueFate: склейка падений отчёта по CrashPrint с ×N; если у отпечатка уже есть Issue падения — «см. #N» вместо стека. Тест IssueFateTest на склейку/ссылку (потеря данных нет — тест только если существующий падает).
