## #470 (главный) + #472 (дубль) — падение при открытии корзины модерации
**Суть.** Администратор открывает вкладку «Корзина» в окне модерации — `IllegalArgumentException: Key "…" was already used` в LazyColumn.

**Где в коде.**
- Ключ строки: `app/src/main/kotlin/com/sperance/exileforge/ui/screens/server/ModerationPage.kt:121` — `items(page.items, key = { it.key })`.
- `ModerationRow.key`: `core/src/main/kotlin/com/sperance/exileforge/core/network/ModerationClient.kt:132` — `heroId.ifEmpty { sanction?.id ?: userId }`, т.е. у героя в корзине ключ — id героя.
- Первая страница кладётся как есть: `core/src/main/kotlin/com/sperance/exileforge/core/admin/ModerationModel.kt:135-140` (`load()`); склейка `Page.followedBy` (`core/.../model/paging/Paging.kt`) убирает дубли только «со стыка» — внутри одной страницы сервера не дедуплицирует.
- Сервер, корзина: `backend/src/main/kotlin/ru/descend/exileforge/features/logic/moderation/ModerationService.kt:286-297` — одна строка на **санкцию** DELETION; `backend/.../data/moderation/Sanction.kt:164` (`SanctionRepository.trash`) — все не снятые и не стёртые удаления без родителя.
- Верхнего кадра нашего кода в стеке нет: стек целиком androidx, `HubTileKt$$ExternalSyntheticLambda0` — склеенная R8 синтетика, не реальный вызов; хвост обрезан («… ещё 51»). Место определено по формату ключа (ObjectId) и действию игрока.

**Корневая причина — данные сервера (не клиентская склейка).** Корзина — список санкций, а ключ строки — id героя. У героя оказалось **две действующие беспредковые санкции удаления** → две строки с одним heroId на первой странице → падение. Как появляется вторая: `ModerationService.delete` (стр. 488-492) для HERO читает героя `heroes.findById` **вне** `HeroLocks`, затем `hide()` (под замком, но без проверки «уже удалён») и `impose()` без проверки наличия действующего удаления. Гонка двух удалений (два сотрудника, либо самоудаление игрока `SelfDeletionService.mark` в тот же момент) даёт две санкции. id `6ac3fdc2…` — ObjectId от ~05.10.2026. Подтвердить в базе: `sanctions.find({kind:"DELETION", targetId:"6ac3fdc25880719c2b335d21", liftedAt:null, purgedAt:null})` (если ключ — id героя) или `_id` (если это санкция).
Побочно: даже без дубля любая будущая гонка снова уронит корзину у всех сотрудников — падение воспроизводится при каждом открытии вкладки, пока дубль в базе.

**Исправлено ли.** Нет. HEAD клиента = коммит 0.17.2 (`44f05452`) + docs; в истории сервера с 15.10 правок корзины/ключей нет; код выше — текущий.

**Сервер затронут.** Да (источник дублей), клиент — тоже (хрупкий ключ).

**Варианты.**
1. *(рекоменд.)* Клиент: в корзине ключ строки — id санкции (`row.sanction?.id ?: key`), и `Page`/`load()` дедуплицирует внутри страницы (`distinctBy(key)`) — падение исключено при любых данных. Сервер: `delete(HERO)` целиком под `HeroLocks.withLock(hero)` с перечиткой героя и отказом `AlreadyDeleted`, если у цели уже есть действующее удаление; разовая чистка: лишние дубли закрыть `liftedAt` (часть `CollectionSchemas`/скрипт — решение владельца). + Плюс: чинит и симптом, и причину. − Минус: два репо.
2. Только клиент (ключ санкции + дедуп). + Быстро, без сервера. − Корзина покажет героя дважды, второе «Восстановить» даст ошибку; гонка остаётся.
3. Только сервер (замок + чистка). + Причина устранена. − Клиент остаётся хрупким для любого будущего дубля; до деплоя падение остаётся.

**Дизайн:** не нужен. **Размер:** 2–3 ч (клиент 0.5, сервер 1–1.5, чистка 0.5). **Форма данных:** не меняется; чистка дублей — разовая правка документов (`PartSchema`/миграция), без вайпа.
**Вопросы владельцу:** чистить дубли автоматически при старте сервера (а) или вручную скриптом (б)? Какой оставить — старший номер (а) или санкцию модерации вместо самоудаления (б)?

## #454 — «Запрос о выборе отправлен, окно зависло» (Разлом недели)
**Суть.** Игрок выбрал вариант узла (удержанием), интерфейс «завис».

**Что видно в отчёте.** Действия `rift/act` идут каждые 2–10 с до 12:46:15 (в логе сервера последний — 12:46:15). Затем «нет ответа сервера ×3» 12:46:29…12:46:52 и `POST rift/act → 0` в 12:46:52; в 12:46:55 `GET hero/view → 304` — сеть вернулась. Сервер запрос не получил (в логе его нет). Стека/падения нет.

**Где в коде.**
- `core/src/main/kotlin/com/sperance/exileforge/core/expedition/RiftActions.kt:161-170` — `act()` через `commands.task(writing = true)`; ключ идемпотентности новый на каждый вызов (`TrialClient.kt:33`).
- `core/.../network/ForgeHttp.kt:23` — `CALL_MS = 30_000` (+ один `SafeRetry`); `core/.../session/CommandRunner.kt:119-145` — всё это время `busy = true`.
- `app/src/main/kotlin/com/sperance/exileforge/ui/screens/expedition/RiftScreen.kt:176` — `idle = !game.busy`; `:937-958` `OfferFooterBar` — `ButtonState.of(idle && …)` → кнопки **Disabled (штриховка), не Busy** — ни спиннера, ни «отправляется».
- После сбоя `CommandRunner.report` даёт тост «Ответ потерян. Запись могла сохраниться: обновите данные перед повтором» (`runtime.uncertain_write`), но **обновить доску на экране Разлома нечем**: `ExpeditionViewModel.refreshRift()` (`ExpeditionViewModel.kt:116`) нигде не вызывается; доска не перечитывается после неудачного `act`.

**Корневая причина.** До 30 с все кнопки Разлома погашены без признака отправки и без признака потери связи → «зависло». Если ответ теряется после записи на сервере, доска на клиенте устаревает, следующий выбор получит отказ, а способа обновить, кроме выхода с экрана, нет.

**Исправлено ли.** Нет (бой-итог `deliver()` уже умеет повтор и плашку «Отправка… попытка N», а шаги узлов — нет).

**Сервер:** не затронут.

**Варианты.**
1. *(рекоменд.)* Шаги Разлома как итог боя: в полёте — кнопка подвала `Busy` (спиннер), через ~3 с — плашка «Отправка…/нет связи, повтор N», повтор с тем же ключом (сервер повтор не выполнит дважды); при неуспехе — автоматическое `refresh()` доски и строка «Связь потеряна — обновить». + Закрывает и #462 (индикация связи). − 3–4 ч.
2. Минимум: `ButtonState.of(idle, busy = game.busy)` в подвале/картах + `refresh()` в `catch` у `act`/`go`. + 1 ч. − Ожидание до 30 с остаётся.
3. Снизить `CALL_MS` для `rift/act`. − Затрагивает общий сетевой слой, риск ложных сбоев на мобильной сети.

**Дизайн:** небольшой — состояние подвала «отправка/нет связи» (можно взять облик `DeliveryPlate` боя). **Размер:** 3–4 ч (вариант 1). **Форма данных:** нет.
**Вопросы владельцу:** повторять шаг автоматически до успеха (а) или после первого сбоя показать «Повторить» (б)? Объединить с #462 в одну задачу (да/нет)?

## #453 — тестировщикам и модераторам сменять своё «предназначение аккаунта»

**Варианты.**
1. *(рекоменд.)* `canRedrawOwnFate(actor) = ADMIN || MODERATOR || аккаунт с героем-тестировщиком`; новый маршрут `POST fate/redraw` (себе, вне `/admin`), без письма, строка журнала `FATE`; в клиенте — пункт в окне тестирования (`TesterPages.kt:40`) и в своём досье модератора. + Чужим менять по-прежнему только админ. − Правка RULES (исключение из «раз и навсегда»).

**Связь:** #482 (предмет смены Предначертания от админа) — та же операция «себе». **Дизайн:** не нужен (лист выбора дара уже есть — `FateGrid`). **Размер:** 2–3 ч. **Форма данных:** нет.

## Предложения по области
- Ключи всех серверных списков (`PagedColumn`) — по id записи, а не по связанной сущности, и дедуп внутри страницы в `Page`: одно место защищает от всего класса падений «Key was already used».
- Все мутации модерации (удаление, бан, переименование) — под `HeroLocks` с проверкой «уже применено» и ключом идемпотентности: двойное нажатие/гонка двух сотрудников перестанут плодить санкции.
- Единый индикатор «Отправка… / нет связи, повтор» для всех команд с ожиданием дольше 2–3 с (сейчас кнопки просто штрихуются до 30 с): убирает целый класс отчётов «зависло».
- В окне модерации — чип «версия ниже актуальной» и фильтр по версии: быстро видно, кто играет на старой сборке и чьи отчёты неактуальны.
- В отчётах модерации — кнопка «Открыть досье автора» и «Копировать номер отчёта/Issue»: меньше ручного поиска при разборе.
