## [LOOT-01] Повторяющиеся строки LOOT-таблицы молча схлопываются

- **Категория:** ECONOMY / BUG. **Приоритет:** P1. **Уверенность:** высокая (тест и симуляция).
- **Подсистема:** таблицы добычи (`TableSet`), сундуки зон, боссы, стражи Ваал-зон.
- **Файлы:**
  - `rules/src/main/kotlin/com/sperance/exileforge/rules/table/Tables.kt:149` — `own.flatMap { it.entries }.forEach { entry -> merged[entry.code] = entry }`;
  - `Tables.kt:136` — `loot(tag) = resolved[tag]?.values`;
  - `src/main/resources/content/tables.json` — `loot:CHEST_2…9`, `loot:BOSS_1…4`, `loot:CORRUPT_1…9`.
- **Ожидание:** запись таблицы в броске добычи катится «на каждую запись независимо» (KDoc `TableEntry`). Содержимое таблиц показывает, что автор поставил две строки `table:drop` намеренно: 0,8 + 0,25. Коммит `f0de26d` «chest table chances within one» разбил шанс больше единицы на две строки.
- **Факт:** `resolve` кладёт записи в `LinkedHashMap` по `code`, поэтому из двух одинаковых кодов выживает последняя. `validateRefs` повторы не ловит. Так работает с сервера 1.0.0: дубли есть во всех 66 ревизиях `tables.json`.
- **Доказательство (тест `audit.LootAudit.duplicateLootEntriesAreLost`):**
  ```
  loot:CHEST_2 raw=13 resolved=11 kept=[item:ORB_OF_ALTERATION@0.01, table:drop@0.25, item:ORB_OF_AUGMENTATION@0.025]
  loot:CHEST_5 raw=13 resolved=12 kept=[table:drop@0.5, ...]
  loot:CORRUPT_9 raw=13 resolved=12 kept=[table:drop@0.975]
  loot:BOSS_1 raw=12 resolved=10 kept=[item:ORB_OF_AUGMENTATION@0.05, item:ORB_OF_ALTERATION@0.02, table:drop@0.2]
  loot:CHEST_2 N=200000 seeds=0..199999 equipment/roll=0.249955 intended=1.05  alteration/roll=0.00998
  loot:CHEST_5 N=200000 equipment/roll=0.500055 intended=1.45
  loot:CORRUPT_9 N=200000 equipment/roll=0.975135 intended=1.975
  ```
  Наблюдение совпадает с теорией «выжила последняя строка»: 0,25 / 0,50 / 0,975, 95% CI ±0,002. Сумма строк, которую задумал автор, — 1,05 / 1,45 / 1,975.
- **Масштаб:** 21 таблица. Потери по видам:
  - вещи сундуков зон (CHEST_2…9): −36…−76%;
  - вещи стражей Ваал (CORRUPT_1…9): −33…−69%;
  - изменения у боссов (BOSS_1…4): сфера изменения 0,125…0,15 → 0,02 (×2 штуки в BOSS_4); сфера приращения в BOSS_1 0,125 → 0,05; сфера изменения в CHEST_2…4 0,25 → 0,01.
- **Воспроизведение:** `TableSet.loot("loot:CHEST_2")` возвращает 11 записей из 13.
- **Последствия:** заметно меньше вещей с сундуков и стражей и меньше базовых сфер с боссов. Симуляция экономики (`simulateEconomy`) идёт тем же кодом, поэтому текущий баланс мог подгоняться под урезанные значения.
- **Варианты решения:**
  1. Разрешить повторы в LOOT-таблицах: `loot()` возвращает записи списком, без схлопывания по коду. Переопределение по коду оставить только для `includes`.
  2. Запретить повторы при загрузке (`fail("table X: repeated Y")`) и свести контент к одной строке: `chance` больше 1 уже поддерживается через `dice.times`.
  3. Оставить как есть и вычистить мёртвые строки из контента.
- **Побочные эффекты:** варианты 1 и 2 меняют результат ролла, поэтому нужен подъём `RULES_VERSION`. Добыча сундуков и стражей вырастет в 1,5–4 раза, это балансное решение.
- **Регрессионный тест:** при загрузке ни в одной таблице не должно быть двух записей с одним кодом, либо `loot(tag).size` равен числу сырых записей.
- **Вопрос владельцу:** две строки `table:drop` — это задуманные две тяги, или под нынешние (урезанные) значения уже подогнан баланс?
- **Рекомендация:** вариант 2 (явная ошибка контента плюс одна строка с `chance > 1`), значения согласовать с владельцем.
- **Статус:** открыто.

## [LOOT-02] Уникалка таблицы падает выше уровня района при поднятом уровне вещи

- **Категория:** BUG. **Приоритет:** P2. **Уверенность:** высокая (симуляция).
- **Подсистема:** добыча забега (`Run.grant` → `LootRoller.pickFrom`).
- **Файлы:**
  - `rules/.../roll/Loot.kt:128-132`: `templatePoolUpTo(tags, level).filter { rarity != MYTHICAL || dropsAt(area) }`;
  - `content/Content.kt:380`: `templatePoolUpTo` → `dropsAt(level)`;
  - вызовы: `run/Run.kt:961` (`grant`), `Run.kt:627` (`treasure`, уровень района +10), `Run.kt:648` (`blightChest`, +2/+4/+6), `Run.kt:570` (монстр карты: уровень района ±`levelSpread` 2).
- **Инвариант:** «У каждой уникалки - уровень падения в контенте (`dropLevel`), и он действует на всех путях … путь, что поднимает уровень вещи над районом, сверяет его с уровнем района (4.9.0, `ContentIndex.uniquePool` с `area` …)».
- **Факт:** с районом сверяются только мифические. Уникалки таблицы шаблонов фильтруются по `dropsAt(level)`, а `level` здесь — уже поднятый уровень.
- **Доказательство (симуляция `audit.LootAudit.uniquesAboveAreaThroughRaisedLevel`):** N = 300 000, семена 0..N−1, таблица `drop`, bonus 500, unique 3,0.
  ```
  area=10 level=20 -> uniques=11105, with dropLevel>area: 1416 (12.8%)
  area=20 level=30 -> uniques=13904, dropLevel>area: 2459 (17.7%)
  area=40 level=50 -> 1655 (7.5%);  area=60 level=70 -> 654 (2.7%);  area=75 level=85 -> 159 (0.6%)
  ```
  Теория правила: 0%. При +2 на выбранных районах (кратных 5) превышений 0. Но `dropLevel` в контенте идут шагом 5 (10, 15, 20…), так что на районе 58 монстр 60-го уровня открывает уникалки с `dropLevel` 60 (вывод по коду).
- **Последствия:** уникалки на 2–10 уровней раньше задуманного, особенно из сокровищниц: сундук сокровищницы всегда +10.
- **Варианты решения:**
  1. В `pickFrom` фильтровать уникалки так же, как мифические: `!template.unique || template.dropsAt(area)`.
  2. Передавать в `templatePoolUpTo` значение `minOf(level, area)` для фиксированных редкостей.
- **Побочные эффекты:** меняется ролл, нужен подъём `RULES_VERSION`. В ранних районах из сокровищниц уникалок станет немного меньше.
- **Регрессионный тест:** по образцу `aRaisedItemLevelBelowTheMythicalAreaDropsNoMythical`, но для `Rarity.UNIQUE` с `dropLevel > area`.
- **Вопрос владельцу:** сокровищница +10 должна открывать более высокие базы, а не уникалки — верно?
- **Рекомендация:** вариант 1.
- **Статус:** открыто.

## [LOOT-03] Уникалки из таблиц шаблонов идут мимо `Run.uniqueChance`

- **Категория:** DESIGN / ECONOMY. **Приоритет:** P2. **Уверенность:** высокая.
- **Подсистема:** шанс уникалки.
- **Файлы:**
  - `rules/.../roll/Loot.kt:114-121`: `pick` — вес уникалки × (1 + bonus/100) × `unique`;
  - `run/Run.kt:959-961`: `rarityBonus = rule.rarityBonus + boost.rarity`;
  - `Run.kt:903`: `uniqueChance` с `context.bonus(UNIQUE).unique`.
- **Инвариант:** «Шанс любой уникалки добычи - одна точка `Run.uniqueChance` с множителем редкости героя `LootRules.uniqueRarity` = `1 + 2·r/(r + loot.uniqueRarityHalf)`; база редкости источника (`RarityRule.rarityBonus`) в r не входит».
- **Факт:** у уникалки из таблицы шаблонов (основной поток вещей монстров и сундуков) вес растёт:
  - линейно по (1 + (rarityBonus + r)/100), как у волшебной и редкой;
  - и ещё на `uniqueRarity(r)`.

  То есть r учтён дважды. Силы `WorldKind.UNIQUE` (POWER_VOID_SIGHT, POWER_TROPHY_TRAIL, POWER_ATLAS_BURDEN) на этот путь не действуют.
- **Доказательство (симуляция `uniqueRarityAndBoost`):** N = 200 000 на точку, уровень 60, семена 0..N−1.
  ```
  srcBonus=0   hero r=0 -> 0.01359 ±0.00051 ; r=100 -> 0.02251 ; r=300 -> 0.03473 ; r=1200 -> 0.06000 ±0.00104
  srcBonus=500 hero r=0 -> 0.02752 ; r=1200 -> 0.06160
  ```
  При r = 1200 путь `Run.uniqueChance` дал бы ×2,0, предел ×3. Табличный путь даёт ×4,4.
- **Последствия:** редкость героя на обычной добыче сильнее, чем обещает формула. Силы «к уникалкам» ничего не дают обычным монстрам.
- **Варианты решения:**
  1. Убрать `unique` из `pick`, а таблицу шаблонов оставить на общем бонусе редкости. Тогда это путь редкости, а не шанса уникалки; RULES уточнить.
  2. Вынести решение «уникалка или нет» в отдельный бросок через `Run.uniqueChance`, а из таблицы тянуть только неуникальные базы.
  3. Оставить, но записать в RULES как вторую задуманную формулу.
- **Побочные эффекты:** заметно меняется частота уникалок. Нужен подъём `RULES_VERSION` и пересчёт экономики.
- **Вопрос владельцу:** какая формула задумана для уникалок из обычной добычи? Должны ли силы «+% уникальных» действовать на обычных монстров?
- **Статус:** открыто.
